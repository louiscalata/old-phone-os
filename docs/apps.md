# Everyday apps

`OPOS_APPS` names the extra apps, comma-separated (`clock,contacts`). When the variable is absent or empty, the main page is unchanged and `/apps` is not served. The Duo image drop-in `packaging/duo-os/opos-apps.conf` names `clock,contacts,notes,calc,calls,convert`. The demo and the postmarketOS build do not set the variable.

Each named app is its own page. The main page gains one link, More apps, inside All apps. `web.page()` does not grow.

App files live under `$XDG_STATE_HOME/opos` (the default state directory when that variable is unset). Writes are atomic and mode 0600. JSON files use an empty `.name.lock` file in the same directory to coordinate publishing and recovery across processes. Recovery reads the current file again while holding that lock. A valid save is used immediately, and a file that remains unreadable is moved aside before the app starts empty. Contacts also holds this lock from loading the saved list through checking the request and publishing any changes. Nothing in this path uses the network. [Unix file locking](https://docs.python.org/3/library/fcntl.html#fcntl.flock) · [Windows byte-range locking](https://docs.python.org/3/library/msvcrt.html#msvcrt.locking)

Each app has a disclosure line: works offline, sends data, uses, real or practice. The helper is not given a way to write these files.

An app that fails to open shows a short page with Home. Phone and the front page keep working.

## AI mode

`OPOS_APPS=ai` enables `/ai` and the token-protected `/api/ai`. AI mode shows a phone model and an optional PC GPU model in two panes. Questions and streamed answers stay plain text. It uses the phone's configured local model; no model is installed by enabling the app. The page can span two screens, stack on a narrow screen, or open one pane per window with `/ai?pane=phone` and `/ai?pane=gpu`. Naming `ai` adds no home-page bytes beyond the shared apps tag.

`OPOS_GPU_LINK=1` separately starts the GPU Link listener with the page server and stops it when the page server ends. Both switches are off by default. The listener binds only to `127.0.0.1`. `OPOS_GPU_LINK_PORT` selects the phone listener port (default `8767`). The companion chooses its own local forwarded port. That computer port must differ from `8767` when the Inference monitor runs there. `OPOS_GPU_LINK_MODEL` names the one model file it can serve. `OPOS_GPU_LINK_MODEL_NAME` sets its display name; without it the file's stem is used. `OPOS_GPU_LINK_LABEL` sets the phone's label (default `OPOS phone`). A link startup failure prints one line without secret values and leaves the page server working. The Duo app drop-in does not enable AI mode or GPU Link.

The answer store keeps `ai-answer-<id>.json` files under `$XDG_STATE_HOME/opos` (or `~/.local/state/opos`). GPU Link keeps the enrolled PC's label and key in `gpu-link-pc.json` and the model's hash and file metadata in `gpu-link-model.json` there. These use private, atomic Store writes and its lock and recovery files. The configured model file stays at its existing path. The page asks the owner to allow or refuse a waiting PC; Forget removes its enrolment and changes the epoch, as does Allow. A signed attempt using the pre-Allow epoch gets the empty 401; the companion must say hello again and retry with the new epoch and a new nonce. See the [enrolment and signed request rules](gpu-link.md#6-signed-requests).

An enrolled PC can see the question and partial answer sent to the GPU pane and keep a copy of the configured model file. The page says, "This PC can see what you ask here." Owner-mode developer access permits more than GPU Link, so only a trusted PC should be enrolled. See [gpu-link.md](gpu-link.md) for the protocol and planned PC companion. The repository supplies `tools/gpu-link-standin-pc.py` for protocol checks with practice text and no reported speed. It does not establish GPU inference or the Windows companion requirements. See [tools/README.md](../tools/README.md) for its use. Physical-phone AI mode and GPU Link execution is not recorded here. Every on-phone AI mode and GPU Link check is **NOT_RUN**. Battery-rule tasks, calls and texts remain simulated.

## Call log

`calls` enables `/calls` and the token-protected `/api/calls`. The log keeps up to 200 calls in `calls.json`, under `OPOS_STATE_DIR` when set, otherwise `$XDG_STATE_HOME/opos` (or `~/.local/state/opos`). It uses the same atomic Store writes as contacts and notes: a private directory (0700) and file (0600). Oldest start times are pruned first. Unreadable or invalid files are moved to `calls.json.bad-<time>` and the log starts empty with a recovery notice. If the copy cannot be kept, the log refuses to overwrite the file. A storage failure does not prevent a call, but that event may be missing from the log.

Each row stores the number, the contact name known at the start (empty when unknown), direction, UTC start time, duration in connected seconds, and whether the modem was practice or real. The page shows newest first, grouped by the viewing phone's local day. Search matches names and numbers. A row opens the existing Phone number form; the owner still taps Call. Clear all calls requires a separate confirmation and also clears the missed count. It does not delete recovery copies. Recording and clearing hold the same file lock from loading the saved calls through publishing the updated list.

Recording happens through the optional modem `call_observer`, using `opos.calllog.record(CallEvent(...))`. An adapter emits `started`, `connected` when answered, and `ended` with a unique 32-character hexadecimal call id, number, incoming or outgoing direction, Unix event time, and an explicit practice flag. The ending event supplies connected seconds from the adapter's monotonic clock, or `None` when unknown. It can also supply `answered` so a lost connected write cannot turn an answered incoming call into a missed one; ScreenModem supplies it. No Modem protocol method changes. Starts are saved immediately with duration unavailable; interrupted calls stay that way after a restart. An unanswered incoming call becomes missed with duration zero. Reading the API does not acknowledge calls: `missed_count` counts missed rows still retained, decreasing on pruning or clear. While the PIN lock is on and the phone is locked, the lock screen's missed-call count is this number; Home does not read it yet.

The current phone uses ScreenModem, so its calls are labelled Practice. Its incoming and answer hooks are local simulation hooks, with no incoming-call UI added here. A future real adapter can use the same observer with `practice=False`; no real modem is connected by this change. Example contacts are used only for practice calls in an empty book. There is no account, network request outside the local server, new package, or new service. Keyboard input, pane layout, and Home use the shared app shell. Every on-device call-log check is **NOT_RUN**.

## While the phone is locked

This applies only with the PIN lock on (`OPOS_LOCK=1`); with it off, nothing here changes. While the phone is locked, a read of an app's API (`GET /api/contacts`, `/api/notes`, `/api/clock`, `/api/calls`) answers with the same body as a locked `/api/state`: `locked`, the clock, the battery percent, and the lock counts. It carries no names, numbers, note titles, alarm labels or call rows. The Clock answer adds whether an alarm is ringing and its time (`Alarm 07:05`), without the label, so Stop and Snooze can still be offered; those two requests and Hang up stay allowed, and their answers are the locked body too. The lock counts are the missed calls kept by the Call log app (0 when that app is off) and the next alarm's time. The message count stays 0: the phone keeps no record of which messages were read, so there is no count of new ones to show. The app pages themselves are fixed documents with no saved data in them.

With the lock on, the served home page gains one tag for `/pin.js`, the PIN pad. Showing the lock screen locks the server. Unlock, a swipe up, Escape, Call and Helper on the lock screen all ask the server: with a saved PIN the pad asks for the digits and sends them, and with no saved PIN the server unlocks without digits. The lock screen comes off only after the server has answered that the phone is unlocked; a wrong PIN, a running wait, or no answer leaves it on. The script does not compare or keep a PIN. It was run in node against a stand-in page (`tests/test_lock_pad.py`); a browser and the phone are **NOT_RUN**.

The lock screen can be showing while the server is still unlocked: the Lock request was lost, or the server refused it (the shared limit on POST requests answers 429). The page therefore trusts an "unlocked" answer only when it asked after the server confirmed that it is locked. Until that confirmation the lock screen says "The phone did not lock. Unlock tries again.", every Unlock and every 5 second check sends the Lock request again (one at a time), and the page sends no status request and no digits, so a phone that did not lock cannot be opened without the PIN from that page. While the Lock request has not gone through, the server itself is still unlocked and still answers reads; the message is there so the owner knows. A 429 to the digits is reported as "The phone is busy", not as a wrong PIN.

The pad is three columns that shrink with the screen (`minmax(0,1fr)` tracks, keys without the 160 px minimum that other lock-screen buttons have), at most 360 px wide and never wider than the lock screen. The test checks these rules; the layout on a 320 px screen was not looked at in a browser (**NOT_RUN**).

Wrong tries: the first four cost nothing. The fifth starts a 30 second wait, and each further wrong try doubles it (60 s, 2 min, ... about 64 minutes at the 12th, about 4 hours 16 minutes at the 14th) up to 8 hours, which the 15th wrong try and every later one get. During a wait every try is refused without being counted, the right PIN included. The count is kept on disk and only the right PIN clears it; restarting the phone does not. Nothing is ever erased: there is no wipe. What this means for guessing through the lock screen: after the first 14 tries (about 8 and a half hours of waits) a guesser gets 3 tries a day, so trying all 10,000 four-digit PINs takes about 9 years, and about 4 and a half years on average. A longer PIN is slower to guess in proportion (an 8-digit PIN: about 91,000 years for all of them). The owner who forgets the PIN is never locked out for more than 8 hours at a time. The limit covers tries made through the server; someone who can read the saved PIN record on the phone's storage can test PINs against it without the server and without any wait.

## Converter

`convert` enables `/convert` and the token-protected `/api/convert`. It converts length (mm, cm, m, km, inch, foot, yard, mile), mass (g, kg, oz, lb), volume (ml, L, US fl oz, US cup, US pint, US gal) and temperature (C, F, K) with fixed factors in `src/opos/convert.py`. The amount is plain decimal text of at most 40 characters and at most 10^12 in size: no exponent, ASCII digits only. Length, mass and volume refuse a negative amount, and a temperature below absolute zero is refused. The result has up to six significant figures. Nothing is stored, and nothing leaves the local server.

The native shell (`src/opos/native/screens.py`) has a Converter screen with the same switch: it reads the measures and works each conversion out in the shell's own process with the same code the server runs (`opos.convert` and the `/convert` page's own handler), so it needs no server and answers the same as `/api/convert` for every input, refusals included. Only when that code cannot be loaded does it ask `/api/convert` instead. Because the shell never runs while the server has a PIN lock (it hands over to the browser), a locked phone never reaches this screen. It asks one conversion at a time and stores nothing. See `packaging/duo-os/NATIVE.md`. The screen has not been run on a phone or under real GTK.

With the PIN lock on and the phone locked, `GET /api/convert` answers with the locked body described above, and a conversion is refused as `locked` (403), like any other app write.

## Not run on a phone

The Duo image names clock, contacts, notes, calc, calls and convert. Each is its own page. The home page only gains the existing short `/apps-home.js` tag, which adds the More apps link and, when an alarm is armed, the words "Alarm" and "Alarm 07:00" on the lock screen. Enabling calls or convert adds no home-page bytes.

No install has been made for this work. Every on-device check in the phone-features spec (D1-D11) is NOT_RUN.

An alarm or timer ring plays `src/opos/sounds/alarm.wav` through `paplay`: six beeps of 0.4 seconds, from 20 to 70 percent of the paplay stream, each one after the last has ended. The sink volume is not changed and no media role is set. A beep that has not ended after 2 seconds is terminated, then killed, so one ring ends within 24 seconds. Stop, Snooze, Delete and switching an alarm off end the beep that is playing and the rest of that ring. A timer ring has no Stop button; it ends by itself within the same 24 seconds. The server runs `paplay` from `PATH`, without a shell, as its own user. The image recipes do not add `paplay`; when it is missing, the alarm shows on screen only and nothing is raised. Whether the server reaches the PulseAudio session on the phone, and whether the tone is heard, is NOT_RUN. Vibration stays off.
